# TRELLIS Multi-Image Fusion Failure Analysis and Internal Geometry Representation

## Core diagnosis

This analysis is grounded in the official TRELLIS and TRELLIS.2 papers, the corresponding entity["organization","Microsoft","software company"] repositories on entity["company","GitHub","developer platform"], the pipeline and model code, the DeepWiki implementation notes, and related literature on occupancy representations, flexible mesh extraction, sparse voxel generation, and high-compression autoencoding. The central conclusion is that your current fusion failures are not an implementation accident. They are mostly a consequence of using independent **single-image generative completions** as if they were **camera-consistent partial reconstructions**. In both the original TRELLIS and TRELLIS.2, the early sparse stage is a **coarse, sampled support layout in an object-centric latent frame**, not a metrically faithful visible-surface observation in camera space. Fine geometry is recovered later by latent decoding. That makes voxelwise overlap a poor proxy for “same geometry across views.” citeturn39view0turn40view2turn35view0turn33view0turn33view1turn12view0

The shortest way to say it is this:

```text
image(s)
  -> image condition tokens
  -> sparse-structure sampler
  -> sparse support coordinates
  -> shape-latent sampler on those coordinates
  -> shape decoder
  -> explicit geometric primitives / mesh
  -> material stage
```

The decisive architectural point is that **global support is chosen at the sparse-structure stage**, while **most detailed geometry is carried by later latent features and decoder outputs**. So fusing after independent sparse-structure sampling is already downstream of the main mode-selection step. citeturn14view0turn14view1turn14view2turn15view0turn35view0turn27view4turn26view1

## What TRELLIS actually represents

In the original TRELLIS paper, the structured latent is explicitly defined as a set of pairs \((z_i, p_i)\), where \(p_i\) is the position of an active voxel in a 3D grid intersecting the asset surface and \(z_i\) is a local latent attached to that voxel. The paper states the meaning very clearly: the active voxels \(p_i\) “outline the coarse structure,” while the latents \(z_i\) “capture finer details of appearance and shape.” It also says those latents are constructed by aggregating multiview DINO features and attaching them to active voxels. That is the cleanest textual evidence for your Hypothesis 3: in original TRELLIS, **the coordinates are the scaffold, and the finer geometry/appearance content lives primarily in the local latent features**. citeturn40view2turn39view1turn41view0

The original TRELLIS decoders reinforce that interpretation. For Gaussians, each local latent is decoded into local Gaussian parameters and only constrained to remain near its voxel. For meshes, each local latent predicts per-voxel FlexiCubes parameters and signed-distance-related quantities, and the mesh is extracted only after that learned local decoding and upsampling process. So even there, the active voxel coordinate is not the final geometry; it is a local anchor around which geometry is reconstructed. citeturn40view3turn40view5turn41view1turn38search1

TRELLIS.2 changes the internal 3D representation, but not in a way that rescues voxel-level multiview fusion. TRELLIS.2 replaces the original DINO-derived SLAT encoding with a **native 3D O-Voxel representation** plus a **Sparse Compression VAE**. The paper and project page describe O-Voxel as a sparse voxel structure storing geometry and material in active voxels, then compressed by SC-VAE into compact structured latents with 16× spatial downsampling. The generation pipeline is still staged: sparse structure first, then geometry latents, then material latents. The paper describes stage one as learning “coarse occupancy priors” and establishing the “global sparse layout,” which is exactly the behavior you are seeing in practice. citeturn33view0turn33view2turn35view0

TRELLIS.2’s decoder code also makes the “true geometry location” more concrete than in the original paper. The shape decoder does **not** treat sparse coordinates as the full geometry. It takes a sparse latent tensor and predicts, per active voxel, continuous **dual-vertex positions**, binary **intersection flags**, and a positive **quad interpolation value**, then converts those together with the voxel coordinates into a mesh using a flexible dual-grid meshing routine. That means the earliest stage where TRELLIS.2 holds geometry in a form close to explicit shape is **after shape-latent decoding**, not at the sparse-occupancy coordinates themselves. The coordinates still matter, but mostly as the topological support on which those decoded geometric parameters live. citeturn26view1turn26view0turn27view4turn29view0turn12view7

This is also where the original SLAT language and TRELLIS.2 language should be reconciled carefully. In original TRELLIS, saying “the true geometry is in \(z_i\), not \(p_i\)” is broadly correct. In TRELLIS.2, the sharper statement is: **the sparse layout encodes where geometric support exists, but the explicit local geometry is decoded from the latent features into dual-grid parameters**. So your intuition is basically right, but the most accurate TRELLIS.2 formulation is “geometry is distributed across object-centric support coordinates plus decoder-derived local geometric parameters, with most fine detail absent from the support coordinates alone.” citeturn40view2turn35view0turn26view1

A related literature comparison helps here. Occupancy Networks represent geometry as a continuous decision boundary directly in function space; by contrast, TRELLIS/TRELLIS.2 use **coarse active support plus learned local decoding**. FlexiCubes and TRELLIS.2’s flexible dual-grid machinery likewise place important shape information in local continuous parameters inside occupied cells, not in binary occupancy alone. DC-AE is relevant because TRELLIS.2 borrows the residual autoencoding idea for aggressive spatial compression, which further increases the gap between “support coordinates” and “final geometry.” XCube is relevant because TRELLIS.2’s early-pruning upsampler is explicitly in the family of sparse, efficiency-oriented 3D generative scaffolds rather than exact voxel correspondences. citeturn38search0turn38search1turn38search2turn38search3turn35view1

## Why the current fusion strategies fail

Your first observation — each view generating a full boat rather than a partial boat — is strongly supported by the architecture. The image-conditioned models in both TRELLIS and TRELLIS.2 receive **image embeddings** through cross-attention, but they do **not** receive camera extrinsics, epipolar constraints, or a multiview reconstruction loss at inference time. In TRELLIS.2, `get_cond()` simply runs the image conditioning model and returns condition tensors; stage one then samples sparse structure from noise under that condition, and stage two samples geometry latents on the chosen support. The paper explicitly says stage one learns coarse occupancy priors and global sparse layout from conditioning images. That is a generative completion setup, not a visible-surface estimator. So “front view produces a complete canonical boat” is exactly what the model has been trained to do. citeturn14view0turn14view1turn35view0turn39view1

The “canonical semantic object manifold” interpretation is therefore not only plausible; it is the strongest reading of the evidence. Still, one nuance matters. The papers and code imply an **object-centric normalized 3D frame**, but they do not expose a dedicated test-time pose canonicalizer. In other words, the system clearly reasons in normalized asset coordinates, but some of the canonicalization is likely **learned statistically** from the conditioning image rather than imposed by a hard geometric module. That makes mode-hopping across nearby global layouts, mirror ambiguities, or front/back ambiguities entirely plausible, especially for long, partially symmetric objects such as marine vessels. This part is a strong inference rather than an explicit author claim. citeturn35view0turn33view0turn14view0

Your union and logit-max results also fit the code path. The shape decoder receives all active coordinates you provide and converts them into one mesh by predicting local geometric parameters on those voxels. There is no later “single-object selection” module that says “keep only one boat hypothesis.” So if union or max fusion preserves multiple incompatible global supports, the decoder will happily expand all of them. In original TRELLIS that same behavior is natural because local latents are decoded independently around active voxels; in TRELLIS.2 it is natural because the final mesh is extracted from all currently active dual-grid cells. That is why union and max preserve semantic richness but accumulate duplicate hull sections, duplicated cabins, or multiple overlapping boats. citeturn26view1turn27view0turn40view5

The collapse under mean / vote / smoothing is also architecturally consistent. Stage one is a **sampled rectified-flow model** over a coarse support grid, starting from random noise. In TRELLIS.2 code, sparse structure is sampled from Gaussian noise, then decoded into a binary support and turned into coordinates. In the original TRELLIS paper, the first-stage output is likewise a dense binary grid compressed by a VAE and generated by a flow model. That means each run samples a support set from a conditional distribution over plausible sparse layouts. Averaging occupancies across misaligned support sets estimates per-voxel marginal occupancy, not a coherent object surface. Thresholding that average keeps only the low-entropy “core” voxels, so large parts of the hull disappear. Your severe collapse is therefore what one should expect when applying an AND-like operation to a stochastic coarse support representation. citeturn14view1turn17view2turn19view0turn40view4turn35view0

Two details make that collapse even worse. First, the sparse stage is **very low resolution** relative to final output, so a one-cell drift already means a large geometric displacement after decoding or upsampling. Second, TRELLIS.2’s cascaded higher-resolution path literally obtains high-resolution coordinates by asking the decoder to **upsample and prune subdivision structure**, then quantizing those coordinates under a token budget. That is a support-proposal process, not a metric registration process. So exact overlap is not the representation’s natural invariance. citeturn14view6turn27view4turn22search2turn35view1

Your “same image ensemble” result is especially diagnostic. If independent samples from the **same** image have low overlap, then the sparse stage is not functioning like a deterministic reconstruction module. It is functioning like a **stochastic hypothesis sampler** from a single-image conditional prior. The code directly supports that reading because each stage is sampled from random noise, and the papers describe rectified-flow generation rather than deterministic inference. One caveat: with a fixed seed the pipeline should be effectively deterministic apart from numerical nondeterminism, so the instability is about **different samples**, not about a hidden random walk inside one seed. But for ensembling across seeds, low voxel consensus is expected. citeturn14view1turn14view2turn35view0turn40view4

Your SLAT-fusion results barely changing the outcome are also consistent with the implementation. In TRELLIS.2, `sample_shape_slat()` creates random latent features **only on the coordinates selected by the sparse stage** and then runs the sparse latent flow model there. DeepWiki states the same hierarchy: sparse structure is the coarse geometry scaffold and a conditioning signal for stage two. If the sparse support is wrong, missing, duplicated, or mode-mixed, stage two cannot create geometry where no coordinates exist. It can only refine latents on the provided support. That is why SLAT fusion is already “too late” to repair most of the damage. citeturn14view2turn12view0turn12view1turn12view5turn21view0

## Hypotheses assessment

**Hypothesis 1 — sparse occupancy is not explicit geometry.**  
**Verdict: mostly confirmed, with one nuance.** The sparse stage is explicit in the narrow sense that it marks active support cells in an object-centric grid. But neither the original TRELLIS papers nor TRELLIS.2 treat those coordinates as the final continuous geometry. Original TRELLIS says active voxels provide coarse structure while local latents provide finer shape and appearance; TRELLIS.2 says stage one predicts occupancy layout while stage two produces geometry latents inside active voxels, and the decoder later predicts dual-grid geometry. So the best characterization is “coarse geometric scaffold / latent support anchors,” not “exact geometry.” citeturn40view2turn35view0turn26view1

**Hypothesis 2 — sparse occupancy coordinates are not metrically stable.**  
**Verdict: strongly supported, but inferential rather than explicitly promised by the authors.** The papers never claim run-to-run or view-to-view metric stability for support coordinates, and the code structure argues against expecting it: sampled flow generation from noise, low-resolution support, later continuous decoding inside voxels, and decoder-driven subdivision/upsampling all make exact overlap the wrong stability criterion. Your experiments are therefore aligned with the intended generative use of the model. citeturn14view1turn19view0turn22search2turn35view0

**Hypothesis 3 — the true geometry lives in local latent vectors rather than sparse coordinates.**  
**Verdict: correct for original TRELLIS, and directionally correct but incomplete for TRELLIS.2.** In original TRELLIS, the paper explicitly assigns coarse structure to \(p_i\) and fine detail to \(z_i\). In TRELLIS.2, the stronger statement is that detailed geometry first becomes explicit when the shape decoder maps latent features to dual-vertex positions, intersection flags, and interpolation parameters. So if the choice is only between `p_i` and `z_i`, `z_i` is the more geometrically meaningful carrier. But in TRELLIS.2 the most explicit pre-mesh geometry is actually the **decoder output on top of those latents**, not the latent tensor by itself. citeturn40view2turn26view1turn27view4

**Hypothesis 4 — TRELLIS reasons in semantic latent manifolds rather than camera-space geometry.**  
**Verdict: strongly supported.** The code path has image-token conditioning but no camera model, and the papers frame the task as image-conditioned 3D generation with sparse occupancy priors and global sparse layout. That makes TRELLIS/TRELLIS.2 fundamentally closer to a single-image asset completion model than to calibrated multiview reconstruction. The latent space is 3D and genuinely geometric, but the inference problem being solved is still “infer a plausible 3D asset from image evidence,” not “triangulate visible geometry from camera-space measurements.” citeturn14view0turn35view0turn39view1

**Hypothesis 5 — the right fusion point is before sparse occupancy generation.**  
**Verdict: yes, for model-native multiview generation.** Because stage one selects the global support, this is the architecturally correct place to fuse multiple views if you want the model itself to synthesize a single coherent object. There is one important exception: if you already have calibrated multiview geometry, a very promising alternative is to **bypass stage one entirely** and feed an externally fused sparse scaffold into stage two, because `sample_shape_slat()` already accepts coordinates directly. That is arguably the best near-term path for engineering-grade marine reconstruction. citeturn14view2turn15view0turn35view0

## Correct insertion points for multiview reconstruction

The cleanest model-native insertion point is **conditioning fusion before stage one**. In TRELLIS.2, the pipeline first calls `get_cond()` and then feeds the resulting condition to sparse structure sampling and geometry-latent sampling. Because the same image-condition pathway is upstream of both stages, a multiview extension should first build one **joint condition representation** from all views, then run a single sparse-structure sample and a single shape-latent sample. This is much closer to the model’s intended semantics than post hoc voxel fusion. citeturn14view0turn15view0turn35view0

For actual reconstruction, however, conditioning-only fusion is not enough unless you also tell the model **which view is which**. The current single-image design has no camera pose input, so concatenating multiple image embeddings without pose information mainly increases semantic evidence; it does not impose geometric consistency. The next architecturally correct step is therefore **pose-aware condition fusion**: per-view image tokens plus explicit view tokens encoding azimuth, elevation, roll, FoV, and optionally intrinsics. Without that, the model can still collapse to a semantic consensus object rather than a camera-consistent one. This is a strong inference from the absence of camera terms in the code and papers. citeturn14view0turn35view0

If your marine-vessel data are calibrated, the most promising engineering path is probably even simpler: **replace stage one with an external multiview scaffold**. You can recover silhouettes, sparse depth, TSDF, or point-cloud support from the views, voxelize that into TRELLIS.2 sparse coordinates at the appropriate latent resolution, and call the shape-latent stage directly on those coordinates. This uses TRELLIS.2 where it is strongest — latent completion, local geometric refinement, and material synthesis — while removing the stage that is currently causing the main disagreement. The code already exposes that seam. citeturn14view2turn26view1turn33view0

A later insertion point does exist, but it is secondary. Because TRELLIS.2’s earliest explicit geometry appears after the shape decoder, you could decode several hypotheses to O-Voxel-style shape features or meshes, fuse there, and optionally downsample the result back into a support layout for a refinement pass. The TRELLIS.2 paper even discusses cascaded inference that downscales a generated higher-resolution shape into sparse structure and reruns later stages for cleanup. That makes decoded-geometry fusion more plausible than raw-voxel fusion. Even so, it is still downstream of the key hypothesis-selection step, so it is unlikely to beat proper multiview fusion before or instead of stage one. citeturn35view1turn22search2turn27view4

## Ranked research directions and implementation suggestions

**First priority: build a joint multiview condition path and run one sparse-structure sample.**  
The fastest serious experiment is to modify the condition path rather than the voxel path. Aggregate all view tokens into one condition tensor, add learned per-view embeddings, and ideally add pose embeddings if camera data are available. Then run one stage-one sample and one stage-two sample. This directly tests whether your current failures are mainly due to independent mode selection upstream of geometry. It is the most architecturally faithful extension of the existing code. citeturn14view0turn15view0turn35view0

**Second priority: bypass stage one with an external multiview scaffold.**  
For marine vessels, this may be the best cost-to-value path. Boats have large, smooth hulls and relatively strong silhouette cues, so calibrated silhouettes, sparse depth, or a rough TSDF can often recover a much more stable coarse hull than TRELLIS.2’s single-image sparse prior. Voxelize that scaffold into TRELLIS.2 coordinates, then use `sample_shape_slat()` and the existing decoder for refinement and material generation. This directly targets the sparse-stage bottleneck your results exposed. citeturn14view2turn26view1turn12view5

**Third priority: train only a new multiview sparse-structure model first, while freezing later stages.**  
Because the evidence points to the sparse stage as the dominant semantic bottleneck, the best retraining schedule is not full end-to-end retraining at first. Train a multiview, pose-aware sparse-structure generator that outputs a single support layout from all views, while freezing the pretrained shape/material latent models and decoders. If that alone materially improves the geometry, you have confirmed the bottleneck location and can decide later whether stage two also needs multiview finetuning. citeturn12view0turn12view5turn35view0

**Fourth priority: if you must fuse late, fuse explicit decoded geometry, not binary supports.**  
If you continue exploring fusion without retraining, stop treating voxel overlap as your main signal. Decode each hypothesis to the shape-decoder output or mesh, establish correspondences in that richer space, and only then merge. In TRELLIS.2 the relevant quantities are dual-vertex positions, intersection flags, and interpolation weights; in original TRELLIS the comparable idea is to fuse decoder-level local geometry rather than support occupancy. This still may not solve the mode-selection issue, but it is a more geometrically meaningful fusion space. citeturn26view1turn40view3

**Fifth priority: use feature-space matching rather than voxelwise agreement for ensembling.**  
A more exploratory direction is to treat each sparse hypothesis as a sample from a support-set distribution and align them in feature space using nearest-neighbor matching or optimal transport over coordinates plus latent features, rather than exact voxel identity. This follows naturally from the architecture: neighboring support sets can decode to similar surfaces because the decoder predicts continuous geometry inside voxels. I would rank this below the previous options because it is more research-heavy and less likely to give immediate wins than fixing the insertion point, but it is a coherent backup direction. This is an inference from the decoder design and support hierarchy rather than an explicit claim by the authors. citeturn26view1turn27view4turn35view0

A good practical test plan is therefore: first, hold stage two fixed and compare three pipelines on the same boat set — single-view baseline, multiview condition fusion before stage one, and external scaffold plus stage two refinement. If the external scaffold wins decisively, TRELLIS.2 should be treated in your stack as a **3D generative refiner**, not as the primary multiview reconstructor. If the multiview condition path starts to win once pose is added, then a TRELLIS-native multiview model is viable. Either outcome is useful, but both are more promising than further work on union / mean / max over independently sampled sparse occupancies. citeturn14view2turn15view0turn35view0

## Final assessment

The strongest reading of the paper-and-code evidence is that your present experiments are failing for the **right architectural reason**. TRELLIS.2 is a high-quality, object-centric, single-image 3D generative model built on a sparse support stage and a richer downstream latent/decoder geometry stage. It is not designed to emit complementary, camera-space partial occupancies from different viewpoints. That is why union preserves too many competing hypotheses, mean collapses them, max merges multiple boats, same-image ensembles disagree, and SLAT fusion changes little once stage one has already committed to inconsistent support. The most promising path forward is therefore either **multiview fusion in the condition stream before stage one** or **replacing stage one with an external multiview geometric scaffold and using TRELLIS.2 for refinement**. For marine-vessel reconstruction, I would prioritize the second path first if camera calibration is available, and the first path first if the goal is a more TRELLIS-native research prototype. citeturn35view0turn14view0turn14view2turn26view1turn12view5
